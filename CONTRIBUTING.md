# Правила разработки и качество кода

Изменения вносятся через pull request в `main`. Приоритеты по порядку: сохранность данных пользователя, правильность расчётов (километраж, доли по ПД, планы), точность печатного листа, понятность кода.

## Рабочий цикл

1. Ветка от `main`: `feat/…`, `fix/…`, `refactor/…`, `docs/…`, `chore/…`.
2. До кода опишите в задаче или PR, что увидит пользователь и как это проверить. Для расчётов и импорта подготовьте примеры на вымышленных данных.
3. Сделайте ограниченное по смыслу изменение. Если меняется формат файла плана или схема БД, добавьте миграцию и тест совместимости.
4. `npm ci` (при первом запуске), затем `npm run format` и `npm run check`.
5. Обновите документацию: `CHANGELOG.md` — если изменилось поведение для пользователя; `docs/architecture.md` — если изменилось устройство программы; новый ADR в `docs/adr/` — если принято архитектурное решение. В README не дублируйте команды и правила.
6. Заполните шаблон PR.

Сообщения коммитов — в формате Conventional Commits, на английском: `feat(planning): split work volume by PD`, `fix(import): read open-ended validity period`. Область (`scope`) — имя контекста или приложения: `passport`, `planning`, `documents`, `import`, `stations`, `desktop`, `ui`, `ci`.

## Архитектура и границы модулей

Устройство программы описано в [архитектурном документе](docs/architecture.md). Здесь — правила, которые проверяет линтер и ревью.

| Слой (тег Nx)         | Может импортировать                         | Нельзя                                     |
| --------------------- | ------------------------------------------- | ------------------------------------------ |
| `type:domain`         | `type:kernel`                               | Angular, RxJS, Node, Electron, SQLite, DOM |
| `type:application`    | `type:domain`, `type:kernel`                | инфраструктуру, Angular, Node              |
| `type:infrastructure` | application, domain, kernel, contracts      | UI                                         |
| `type:feature-ui`     | application, kernel, ui-kit                 | инфраструктуру, Node                       |
| `type:app`            | всё — только чтобы связать порты и адаптеры | бизнес-логику                              |

- Домены разных контекстов (`scope:`) не импортируют друг друга. Связь — через опубликованные порты (`PassportView`) и запросы слоя приложения.
- Каждая библиотека экспортирует наружу только `index.ts`. Импорт из чужих внутренних файлов запрещён.
- Новый порт объявляется в слое приложения как интерфейс с узким набором операций. Реализация живёт в инфраструктуре, фейк для тестов — рядом с интерфейсом.

## TypeScript

- `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` включены и не отключаются. Ошибку типов исправляют, а не прячут.
- Нет `any`. Нет `as` для обхода проверки, кроме разбора уже проверенных zod-данных в адаптерах. Нет `!` (non-null assertion) вне тестов.
- Доменные значения — неизменяемые объекты (`readonly`, `Readonly<…>`). Изменение состояния — новая версия объекта.
- Разные единицы — разные типы: метры, километры, координата `{км, м}`, координаты листа в миллиметрах и пикселях не смешиваются. Для этого используются брендированные типы (`Meters`, `SheetMm`) и объекты-значения, а не голые `number`.
- Варианты — размеченные объединения (`kind: 'line' | 'station'`) с исчерпывающим `switch` и проверкой `never`.
- Доменные нарушения возвращаются как `Result<T, DomainError>`; исключения — только для ошибок программиста и сбоев инфраструктуры.
- Идентификаторы в коде — на английском, предметные значения и тексты для пользователя — на русском. Соответствие терминов ведётся в таблице ниже; новый термин сначала добавляют сюда, потом в код:

## Angular

- Только standalone-компоненты, `ChangeDetectionStrategy.OnPush`, signals (`input()`, `output()`, `computed()`), новый control flow (`@if`, `@for` с `track`).
- Компонент рисует модель и передаёт ввод в фасад. Расчётов геометрии листа, долей, планов в компонентах нет — они в слое приложения и домене и приходят готовой моделью.
- Состояние контекста — сервис-фасад на signals; NgRx не используется.
- Лист рисуется SVG и HTML по модели листа. `innerHTML`, `bypassSecurityTrust*` и вставка неочищенного текста в атрибуты SVG запрещены.
- Тексты интерфейса — на русском; подписи кнопок и полей собраны в одном месте фичи, чтобы справка и тесты ссылались на одни строки.

## Electron

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, строгий CSP. Навигация, `window.open` и внешние URL блокируются.
- preload выставляет один объект `window.eow` с методами контракта и ничего больше.
- Каналы IPC, схемы zod и DTO объявлены в `libs/ipc/contracts`. Только `invoke/handle` и одно событие прогресса для долгих операций. Доменные объекты через IPC не передаются — только DTO с мапперами.
- Пути к файлам приходят только из системных диалогов или из списка последних файлов.

## Хранение данных

- **SQLite.** Миграции — пронумерованные SQL-файлы, только вперёд; применённую миграцию не меняют. Перед миграцией и перед вводом редакции в действие делается резервная копия через backup API. Запись — в транзакциях, внешние ключи включены, режим WAL. Запросы — через Kysely с типами, сырые строки SQL собираются только из параметров.
- **Файл плана.** В файле указаны номер версии формата и версия программы. Чтение проходит цепочку миграций и проверку zod; на каждую версию есть файл-образец в тестах. Запись атомарная: временный файл, затем переименование, плюс `.bak`.
- **Импорт.** У каждой формы есть распознаватель по набору заголовков, парсер в сырые строки, перевод в понятия домена и генератор вымышленной фикстуры. Ошибка разбора указывает файл, лист, строку и столбец.

## Тесты

| Что проверяем                          | Как                                                                          |
| -------------------------------------- | ---------------------------------------------------------------------------- |
| Километраж, участки, разбор «км + пк»  | Vitest + fast-check: свойства на нестандартных км, круговой разбор и печать  |
| Доли по ПД, расчёт плана, просрочка КР | Vitest на вымышленных данных; эталон — суммы, сверенные вручную              |
| Сценарии                               | Vitest с фейковыми портами, включая отмену действий и смену редакции         |
| Адаптеры                               | миграции SQLite на временной базе, миграции файла плана, импорт каждой формы |
| Листы                                  | Playwright: эталонные снимки на Windows, PDF 420 × 297 мм, встроенные шрифты |
| Excel                                  | книга открывается, формулы считаются, итоги совпадают с расчётом домена      |

- Порог покрытия строк для `libs/*/domain` — 90 %; для остальных порога нет. Тесты пишутся ради поведения, а не ради процента.
- Тест падает по одной причине и называется как правило: `it('относит разницу нестандартного км на пк 10')`.
- Эталонный снимок обновляют только вместе с объяснением в PR, что изменилось на листе.
- Часы и идентификаторы в тестах фиксированы через порты `Clock` и `IdGenerator`.

## Оформление и линтеры

- Prettier: без точек с запятой, одинарные кавычки, ширина строки 100. `.editorconfig`: UTF-8, LF, два пробела.
- ESLint (angular-eslint, `@nx/enforce-module-boundaries`) и oxlint (`correctness` — ошибка). Правило не отключают ради одного случая; если без этого не обойтись — `eslint-disable-next-line` с причиной в том же комментарии.
- Скрипт `lint` только проверяет файлы, исправляет `lint:fix`.

## Зависимости и лицензии

- Новая зависимость, которая попадает в программу, должна иметь разрешительную лицензию (MIT, BSD, Apache-2.0, ISC; для шрифтов — OFL). Сборка проверяет лицензии и останавливается на копилефте и неизвестной лицензии.
- В PR укажите, зачем нужна зависимость, её лицензию и почему не хватает уже подключённых.
- Версии фиксируются в `package-lock.json`. Обновления зависимостей — отдельными PR.

## Данные и конфиденциальность

- Реальные выгрузки, база паспорта, планы, PDF листов и их фрагменты в репозиторий не добавляются — ни в код, ни в тесты, ни в issue, ни в снимки экрана. `check:public` проверяет это в CI.
- Для тестов используются только вымышленные данные из `npm run fixtures`.
- В снимках экрана для PR — только вымышленный проект.

## Ревью и готовность

PR принимается, когда:

- `npm run check` проходит в CI на Windows и Linux;
- есть тесты на изменённое поведение, а для листов — обновлённые снимки с объяснением;
- старые файлы планов открываются, если затронут формат;
- документация и `CHANGELOG.md` отражают изменение;
- в описании сказано, что изменилось, почему, на каких примерах проверено и что осталось непроверенным.

Не отмечайте функцию как готовую в README и CHANGELOG, пока она не работает в программе.
