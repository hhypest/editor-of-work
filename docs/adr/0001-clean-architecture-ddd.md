# ADR-0001. Clean Architecture и DDD с границами модулей Nx

**Статус:** принято · **Дата:** 20.10.2026

## Контекст

Программа будет жить годами: меняются формы выгрузок ЕК АСУИ, оргструктура дистанции и нормативы, а годовые планы должны открываться через несколько лет без изменений. Предметные правила (километраж, доли по ПД, потребность в ремонте) — самая ценная и самая рискованная часть кода. В HTML-прототипе расчёты, разметка и хранение были перемешаны, поэтому ошибки в долях по ПД и в раскладке листов находились только при печати.

## Решение

- Код делится на слои **домен → приложение → инфраструктура / представление**. Зависимости направлены только к домену.
- Домен — чистый TypeScript без Angular, RxJS, Node, Electron, SQLite и DOM. Время и идентификаторы приходят через порты `Clock` и `IdGenerator`.
- Слой приложения содержит сценарии и интерфейсы портов (`PassportRepository`, `PlanStore`, `PassportView`, `PdfExporter` и др.). Реализации портов — в инфраструктуре; связываются в composition root (`apps/ui`, `apps/desktop`).
- Предметная область делится на ограниченные контексты: **Паспорт дистанции**, **Планирование ППР**, **Документы** (модели чтения), **Импорт** (антикоррупционный слой). Домены контекстов не импортируют друг друга.
- Монорепозиторий Nx: у каждой библиотеки теги `type:` и `scope:`, правило `@nx/enforce-module-boundaries` проверяется линтером в CI.

## Последствия

- Расчёты тестируются без браузера и без базы — быстро и на свойствах (fast-check).
- Смена формы выгрузки затрагивает только парсер импорта, смена UI-библиотеки — только представление.
- Больше файлов и шаблонного кода (порты, мапперы DTO). Это осознанная цена за проверяемость.

## Рассмотренные варианты

- **Один слой «компоненты + сервисы»**, как в прототипе, — быстрее на старте, но правила снова смешаются с отображением.
- **Event Sourcing / CQRS с шиной** — избыточно для одного пользователя; из CQRS взяты только модели чтения для листов.
